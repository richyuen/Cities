## API contract — verified live via `page.evaluate`, all correct
Ran a scripted probe against the live `ctx.modules.get('zoning').api` on a bare rect, not just reading source:
- `costFor(rect, 'c', 2)` → `{cells:12, cost:2280}`, and **confirmed pure**: `world.cells` type-count unchanged before/after the call (no mutation).
- `setZoneRect(...)` with identical args → same `{cells:12, cost:2280}` (`matchesPreview: true`), and `world.cellAt(i,j)` now reads `{type:'zone', zone:'c', density:2}`. `getZoneStats().c` jumped from `{cells:48}` to `{cells:60}` in the same tick — **no debounce lag**, matches the doc comment that stats are computed fresh every call unlike the visual rebuild.
- `clearZone(rect)` → returns `12`, cell reverts to `{type:'none', zone:null}`.
- `setZoneBrush(cellList, 'i', 3)` → `{cells:12, cost:2808}`, cell becomes `{type:'zone', zone:'i', density:3}`.
- Simulated a build (`world.setCell(i,j,{type:'building'})`) on a zoned cell: `getZoneStats().i.cellsBuilt` incremented 3→4 immediately, and the cell **still carries `zone:'i'`** even though `type` is now `'building'` — exactly the mechanism that makes the overlay disappear on built cells (rescan only buckets `cell.type === 'zone'`) while stats keep the zone attribution. Confirmed visually too: in every default-variant screenshot the one "built" lot per demo block shows bare ground, no overlay.
- `showPreview(i,j,w,h,'r')` → `zoning-preview` mesh becomes `visible:true`; `hidePreview()` → `visible:false`. Both correct.

This is the strongest part of the round: the implementation matches the documented contract to the letter, verified behaviorally, not just by reading the code.

## Code review
- `Math.random`: **none** (grepped `src/zoning/**`).
- Folder isolation: contains only `index.js`, `geometry.js`, `showcase.js`. Clean.
- **Dispose correctness, checked specifically**: `dispose()` disposes `S.plateGeo` (own geometry), the preview mesh's `BoxGeometry` (own), and the 3 cloned zone materials (own clones, also removed from `ctx.materials.cache`). It deliberately does **not** dispose the geometry returned by `ctx.materials.bevelBox()` used by the showcase's placeholder buildings. Verified in `src/core/materials.js:140-148` that `bevelBox` is a genuine shared cache keyed by `(w,h,d,bevel,segments)` (`this._geos.get(key)`/`.set(key)`) — a core-owned resource other modules/showcases reuse. Disposing it from `zoning.dispose()` would be the actual bug; skipping it is correct. Same reasoning applies to the demo buildings' `ctx.materials.plastic('mediumStoneGrey', ...)` material, also a shared cache entry, also correctly left alone. No leak found.
- Debounce (`markDirty`/`DIRTY_DEBOUNCE = 0.12s`): each `markDirty()` call resets `dirtyTimer` back to `0.12`, so bursts of `world:cell`/`zone:changed` events correctly coalesce into a single `rescan()` on the trailing edge. `getZoneStats()` is intentionally *not* behind this debounce (confirmed live above) — correct per its own doc comment.
- Minor nit: `S.rng = ctx.rng.fork('zoning')` is created in `init()` but never referenced anywhere in the module (no randomness is needed for a deterministic color/height overlay). Harmless dead field, not worth more than a mention.

## Ranked issues (most damaging first)

1. **Night legibility breaks the density/rim cue and reads as an opaque floor tile, not a translucent "ghost" overlay** — `shots/zoning/r1/zoning_default-21h5.png` (as specifically requested) and `zoning_closeup-21h5.png`. In daylight the "brighter rim" cue works well (see issue-list item 3 below), because `geometry.js` bakes bright/dim shading into a vertex-color attribute that only affects the *diffuse* term, and `DENSITY_BRIGHT` similarly modulates via `InstancedMesh.instanceColor` (also diffuse-only). At night, ambient/sun contribution collapses toward zero, so the only thing left visible is the flat, uniform `emissiveIntensity = night * NIGHT_GLOW` (0.85) term — which is *not* modulated by either vertex color or instance color. The result: every cell in a zone renders as one flat, fully saturated block with no rim/top distinction and no visible height-based brightness difference, and the color reads as solid/opaque rather than glowing translucent plastic — there's also no soft bloom halo bleeding past the plate edges, just a hard-edged saturated rectangle. This directly fails the brief's night-legibility ask ("emissive glow... taller+brighter rim" should still read) and matches the rubric's "night with no emissive life" deduction in spirit even though the color itself does light up.
   - Fix: make the density/rim cue survive into emissive too — e.g. multiply `emissiveIntensity` per-instance by the same `DENSITY_BRIGHT` factor (already have the instance color slot) and/or feed the vertex-color attribute into an emissive multiplier via `onBeforeCompile`, so rim faces glow brighter than tops at night the way they do by diffuse in daylight. Consider also lowering `NIGHT_GLOW` slightly and adding a touch more transmission/opacity at night so the "unbuilt ghost" feel survives after dark instead of looking like a solid poured pad.

2. **Industrial zone's official Blox "brightOrange" (#F58624) desaturates to a muddy yellow-olive, not orange** — visible in nearly every daylight shot, e.g. `zoning_default-12.png`, `zoning_closeup-6h5.png`, `r1-density/zoning_closeup-6h5.png`, and the far-overview extra shot. The combination of low `BASE_OPACITY` (0.34), `transmission: 0.1` letting the green grass show through, and `INTERIOR_SHADE` (0.8) dimming the top face pulls the rendered hue toward yellow-green instead of orange. It's not a color *collision* with another zone (only 3 hues used), but it undercuts "official Blox colours" (REFERENCE.md §1) and makes the industrial zone read as a generic "yellow" rather than a distinct, confident orange at a glance — weaker color-coding legibility than r/c.
   - Fix: either bump industrial's base opacity/reduce transmission relative to r/c so orange survives the grass blend, or shift the top-face `INTERIOR_SHADE` per-zone (industrial could keep more saturation) rather than one constant for all three.

3. **Minor: transparent zone patches show a hazy double-layered "ghosting" at low grazing angles over long distances** — `shots/zoning/r1-density/zoning_closeup-12.png`, top-left/top-center background. Likely a mix of alpha-blend draw-order (no explicit back-to-front sort needed since these are simple flat translucent boxes, but combined with aerial-perspective fog it produces a faint doubled-grid look on the far patches). Low severity — could also just be the intended aerial-perspective haze reading a bit busier than intended on a checkerboard pattern. Worth a look if a future round is styling the density showcase, not urgent.

## What already works well
- **The documented API is implemented exactly as specified and behaves correctly under live testing** — `costFor` is a true pure preview, `setZoneRect`/`setZoneBrush` mutate identically and return matching costs, `clearZone` respects built cells, `getZoneStats` is never stale, and the overlay-disappears-on-build mechanism (`type` flips away from `'zone'` while `zone` field is retained for stats) is correct and confirmed both programmatically and visually.
- **Draw-call budget is hit precisely as designed**: one `InstancedMesh` per zone colour + one preview mesh, confirmed by traversing the `zoning` scene group directly rather than trusting the whole-scene counter. gpuMs is 6.3–11ms against a 20ms budget in every shot — comfortable headroom.
- **The daytime density/rim cue and lot-separation read well**: `MARGIN`-inset plates give a believable "individual lots" texture instead of a solid carpet, and the bright-rim/dim-top vertex coloring is clearly visible at oblique angles in daylight (e.g. `zoning_closeup-6h5.png`), plus `dispose()` correctly distinguishes zoning's own owned geometry/materials from the shared core `bevelBox`/`plastic` caches it must not touch.
